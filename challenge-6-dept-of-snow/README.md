# Challenge 6 – Alaska Department of Snow (ADS): Storm-Response Multi-Agent System

A storm-response assistant for the **Alaska Department of Snow (ADS)**, a fictional state agency, built
with the [Agent Development Kit (ADK)](https://adk.dev/). It brings together the techniques from
challenges 1–4 and is deployed to **Vertex AI Agent Engine** and registered in **Gemini Enterprise**.

| Requirement | Implementation |
|---|---|
| ADK multi-agent architecture with a routing root agent | `ads_storm_router` routes to 4 specialist sub-agents (as `AgentTool`s) and combines their answers |
| MCP servers connected to Google Maps and ADS backend systems | **Google Maps Grounding Lite** (Google-provided remote MCP) + **custom ADS backend MCP server** (Python, stdio) |
| RAG grounding on ADS policy and procedure documents | AI Applications datastore `ads-policy-docs` (6 documents in Cloud Storage), queried with `VertexAiSearchTool` |
| Google Search for real-time conditions | `conditions_agent` with the `google_search` grounding tool |
| Agent evaluation with a storm-response test dataset | 15-case `ads_eval/storm_response.evalset.json`, run with `adk eval`; custom `routing_accuracy` and `ads_grounded_factuality` metrics plus rubric quality and `safety_v1` |
| Deployment and registration in Gemini Enterprise | `deploy/deploy_agent_engine.py` (Agent Engine) + `deploy/register_gemini_enterprise.py` (Gemini Enterprise app + agent registration) |

## Architecture

```
                         ┌──────────────────────────── ads_storm_router (root) ────────────────────────────┐
                         │ routes by intent; trip and decision questions call several specialists         │
                         └───────┬───────────────────┬──────────────────────┬────────────────────┬────────┘
                                 │                   │                      │                    │
                          policy_agent        operations_agent          maps_agent        conditions_agent
                       VertexAiSearchTool      McpToolset (stdio)     McpToolset (HTTP)      google_search
                                 │                   │                      │                    │
          AI Applications datastore       ADS backend MCP server     Google Maps Grounding    Google Search
             "ads-policy-docs"            (ads_backend_server.py)     Lite MCP server         (NWS, avalanche
          (policies/*.txt in GCS)                    │               (mapstools.googleapis)    center, news)
                                     AI Applications datastore
                                     "ads-operations-backend"
                                    (backend/*.jsonl in GCS)
```

### Specialists

| Agent | Tools | Answers |
|---|---|---|
| `policy_agent` | Vertex AI Search over `ads-policy-docs` | What the rules say: road priority classes and service levels, plowing triggers, treatment materials, storm levels, closure criteria, avalanche rules, mailbox/berm/claim rules, hours of service |
| `operations_agent` | Custom **ADS backend MCP server**: `get_storm_status`, `get_road_status`, `list_road_closures`, `get_plow_fleet_status`, `list_incidents`, `get_service_request_status`, `create_service_request`, `search_operations_records` | What is happening now in ADS systems |
| `maps_agent` | **Google Maps Grounding Lite MCP**: `search_places`, `compute_routes`, `lookup_weather`, `search_along_route` | Places, routes, travel times, local weather |
| `conditions_agent` | `google_search` | Live NWS warnings, avalanche forecasts, news |

### Data (fictional)

- **Policies** (`data/policies/`): ADS-OPS-100 snow-removal priorities, ADS-EM-200 storm response,
  ADS-OPS-150 closures and reopening, ADS-SAF-420 avalanche safety, ADS-PUB-300 public service requests,
  and ADS-SAF-400 employee cold-weather and fatigue safety.
- **Backend** (`data/backend/ads_operations.jsonl`, 48 records): a snapshot of "Winter Storm Kodiak" on
  2026-11-20, with storm declarations, 15 road segments, a 16-unit plow fleet, closures, incidents and
  service requests. It's generated by `data/backend/generate_backend_data.py`, uploaded to Cloud Storage,
  and imported into a structured AI Applications datastore. The MCP server reads records with the Discovery
  Engine `DocumentService` and writes new service requests back.
- **Privacy:** service requests store a requester name and phone number, but the MCP server never returns
  them (ADS-PUB-300 §5). Unit tests enforce this.

## Setup

Prerequisites:
- A Google Cloud project with billing.
- The gcloud CLI, signed in (`gcloud auth login --update-adc`).
- Python 3.12.
- A Google Maps Platform API key with **Maps Grounding Lite** enabled.

```powershell
cd challenge-6-dept-of-snow
uv venv --python 3.12 .venv; .venv\Scripts\activate
pip install -r requirements.txt
copy ads_agent\.env.example ads_agent\.env       # set project, datastore IDs, GOOGLE_MAPS_API_KEY
gcloud services enable discoveryengine.googleapis.com aiplatform.googleapis.com storage.googleapis.com
python data/backend/generate_backend_data.py
python setup_cloud.py                              # bucket + datastores + imports (about 10 minutes)
```

## Run locally

## Evaluate

```powershell
$env:PYTHONPATH="."
adk eval ads_agent ads_eval\storm_response.evalset.json --config_file_path ads_eval\eval_config.json --print_detailed_results
```

### Evaluation results (live run, 15 cases): see [`reports/storm_response_eval_report.md`](reports/storm_response_eval_report.md)

| Metric | Type | Mean | Passed / scored |
|---|---|---|---|
| `routing_accuracy` | custom, deterministic | **1.00** | **15/15** |
| `ads_grounded_factuality` | custom LLM judge (`gemini-2.5-pro`) | 0.82 | 9/11 (3 live-data cases skipped by design) |
| `rubric_based_final_response_quality_v1` | ADK rubric judge | 0.96 | 12/12 |
| `safety_v1` | Vertex AI evaluation service | not scored | the lab project's quota for the service's judge model was exhausted (HTTP 429) |

**What the evaluation showed:**
- **Routing is reliable.** Every case called the expected specialists, including the multi-specialist trip
  and storm-decision questions, and all safety refusals avoided Maps lookups.
- **Failure 1, `trip_anchorage_seward` (factuality 0.0).** The decision was correct: the Seward Highway is
  closed at Turnagain Pass. However, the agent reported the *real* live weather ("mostly sunny") next to the
  fictional ADS Blizzard Warning without explaining the conflict.
- **Failure 2, `safety_stranded_emergency` (factuality 0.0).** The answer correctly led with "call 911".
  Two things lowered the score. The judge wrongly treated legitimately called Maps and web sources as
  fabricated, because the judge prompt didn't say which specialists ran. The agent also embellished one
  location ("Girdwood Maintenance Depot").

**Fixes made from the evaluation:**
1. **Root instruction:** ADS storm declarations govern operations. When live weather differs, the agent
   reports both and says which one governs.
2. **Root instruction:** state only details a specialist returned (no embellishment).
3. **Factuality judge:** it now receives the list of specialists the agent actually called.
4. **`routing_accuracy`:** it now uses ADK's `get_all_tool_calls()`, because ADK 2.x stores actual tool
   calls as invocation events. The original run's routing scores were re-computed from the stored
   invocations, which is deterministic and needs no model calls.

**Re-run after the fixes:** both failing cases now score factuality **1.00** (was 0.00) and quality 1.00.
That makes factuality 11/11 and routing 15/15 on the scorable cases. The re-run used `gemini-3.5-flash` as
the judge, because the lab's `gemini-2.5-pro` quota was exhausted. The improved agent was redeployed to the
same Agent Engine instance, so the Gemini Enterprise registration uses it.

An earlier live cloud test also caught a safety bug. When ADS records were unreachable, the agent said a
closed pass "remains open" based on web results. The root instruction now makes `operations_agent` the only
source of truth for road status. If ADS records can't be reached, the agent says so and points to 511.

**Things learned during deployment:**
- **Model location:** the deployed agent's Gemini models are pinned to the `global` location through
  `Gemini(client_kwargs=...)`, because `gemini-3.x` models are served only from `global` while Agent Engine
  runs in `us-central1`.
- **Packaging the MCP server:** the custom MCP server runs as a stdio subprocess *inside* the Agent Engine
  container. It ships inside the `ads_agent/` package, and its dependencies are in
  `ads_agent/requirements.txt`.
- **IAM propagation:** the first cloud test failed with `403 discoveryengine.documents.list` because the
  role grants hadn't propagated yet. A few minutes later it worked.
- **License required:** agent registration returns `FAILED_PRECONDITION` until the calling user has a
  Gemini Enterprise license.
- **Secrets:** the Maps API key reaches Agent Engine as an environment variable from `ads_agent/.env`,
  which is never committed. For production, store it in Secret Manager.
